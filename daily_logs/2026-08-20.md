## 🧠 What I Learned / Key Takeaways

* A traditional LLM primarily generates responses from its training and provided context. An agentic system combines an LLM with instructions, tools, memory, data, and an agent loop so it can complete multi-step tasks.
* The three central parts of an agent are the **model, system prompt, and tools**.
* An agent loop generally follows this pattern: receive a request, reason about the goal, select a tool, observe the result, continue reasoning, and produce a final response.
* Tools are callable functions that extend an agent beyond text generation. They can query databases, call APIs, inspect AWS resources, write files, or perform infrastructure actions.
* **Strands Agents** is an open-source SDK developed by AWS for building agents with Python or TypeScript. It abstracts tool registration, model communication, conversation management, and the agent loop.
* A Python function can be exposed to a Strands agent by using the `@tool` decorator and providing a clear name, description, inputs, and return value.
* **MCP, or Model Context Protocol**, is an open standard that allows AI applications to discover and use external tools, resources, and prompts through a consistent interface.
* MCP does not replace APIs. An MCP server can sit in front of existing APIs and expose their capabilities in a standardized, agent-friendly format.
* **A2A, or Agent-to-Agent protocol**, supports communication and interoperability between independent agents.
* In an **agents-as-tools** design, a supervisor agent treats specialized subagents as callable tools.
* Multi-agent systems can use supervisor/orchestrator patterns, graph-based routing, peer collaboration with shared memory, sequential workflows, or a composite of several patterns.
* Reactive agents wait for user input. Proactive or autonomous agents can monitor conditions and initiate actions without a new prompt.
* Agents require measurable goals, enterprise data access, short- and long-term memory, observability, security controls, and guardrails.
* Human approval remains important for sensitive production actions such as modifying security groups, blocking IP addresses, isolating EC2 instances, or applying Terraform changes.
* Infrastructure changes made directly by agents can create drift from Terraform. A safer pattern is to let the agent propose Terraform code, have a human review it, and deploy it through the established repository and pipeline.
* **Amazon Security Lake** centralizes security data from AWS, on-premises environments, other clouds, and third-party sources.
* Security Lake normalizes security information using **OCSF—the Open Cybersecurity Schema Framework**.
* A security-analysis agent can use **Amazon Athena** to run SQL queries against Security Lake data.
* **AWS Glue Data Catalog** stores metadata such as table names, columns, data types, formats, partitions, and data locations.
* A **Glue crawler** examines a data source, infers its schema, and creates or updates metadata tables in the Glue Data Catalog.
* A **Glue ETL job** extracts, transforms, and loads data. The crawler discovers structure; the ETL job processes the actual data.
* A Security Lake agent may need separate tools to list available tables, retrieve schemas from Glue, and submit SQL queries through Athena.
* **DynamoDB** can store business context about AWS accounts, including environment, criticality, compliance scope, owner, and security contact.
* Technical findings become more useful when they are combined with business context. A compromised production account containing regulated data should be prioritized differently from a development sandbox.
* **Amazon Bedrock** provides managed access to foundation models. Different agents can use different models based on task complexity, latency, and cost requirements.
* **AgentCore Runtime** provides a managed environment for deploying, scaling, and exposing agents through application endpoints.
* Production agentic systems must account for performance, scaling, security, identity, observability, data consistency, governance, cost, and regulatory requirements.
* Agent silos occur when separately built agents use isolated data, security systems, and integrations that prevent them from working together effectively.
* The semantic data layer prepares enterprise information for agents. AWS Glue can perform ETL, while Amazon Neptune can represent relationships as graph data.
* Agent evaluation should examine accuracy, robustness, latency, tone, security, task-completion rate, cost, and measurable business outcomes.
* Agentic-AI projects should begin with a real business problem and a value model rather than introducing agents simply because the technology is interesting.
* **AI-DLC** applies AI throughout the development lifecycle. Humans increasingly guide the work through a loop of **prompt, review, and redirect**.
* A common SaaS architecture can use ECR, ECS/Fargate, RDS, Lambda, SQS, SNS, S3, CloudFront, Route 53, ACM, an Application Load Balancer, CloudWatch, IAM, and Secrets Manager.
* **ECR stores container images**, while **ECS runs and manages containers**. Fargate supplies serverless compute for ECS tasks.
* **RDS** provides managed relational databases, while DynamoDB is a NoSQL database better suited to particular access patterns.
* **SQS** queues work and normally distributes messages among consumers. **SNS** publishes messages to multiple subscribers. A common fan-out design is SNS publishing to multiple SQS queues.
* **Lambda** works well for event-driven and asynchronous tasks, especially when paired with services such as SQS or S3.
* **S3** provides scalable object storage, while **CloudFront** caches and delivers content closer to users.
* **Route 53** manages DNS, **ACM** provisions TLS certificates, and an **Application Load Balancer** distributes HTTP/HTTPS traffic across application targets.
* **CloudWatch** collects logs and metrics, supports alarms, and provides CloudWatch Logs Insights for querying log data.
* **IAM** controls which users, roles, applications, and AWS services can perform specific actions.
* Secrets should be stored in **AWS Secrets Manager** or **Systems Manager Parameter Store**, not hard-coded into application source code.
* Development, staging, production, and sandbox environments can be isolated in separate AWS accounts and reproduced through infrastructure as code.
