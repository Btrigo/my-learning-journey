## 🧠 What I Learned / Key Takeaways

### Filesystems

- A **filesystem** defines how files, directories, names, metadata, and free space are organized on a storage volume.
- A physical disk, partition, volume, filesystem, and drive letter are related but different concepts:
  - A **disk** is the physical or virtual storage device.
  - A **partition** is a defined region of that disk.
  - A **volume** is a usable storage area Windows can mount.
  - A **filesystem** organizes the volume’s contents.
  - A **drive letter** such as `C:` is one way Windows exposes the volume.
- **FAT** means File Allocation Table. It is an old family of relatively simple filesystems.
- **FAT32** remains common on removable media and broadly compatible devices, but a single FAT32 file can be no larger than **4 GiB minus 1 byte**.
- FAT32 is not inherently limited to a 32-GB volume. The familiar 32-GB figure is primarily a limit imposed by Windows’ built-in FAT32 formatting tools; other implementations can create larger FAT32 volumes.
- **HPFS**, or High Performance File System, was historically used with OS/2 and some early Windows NT environments. It is not the normal filesystem for current Windows installations.
- **NTFS** means New Technology File System. Modern Windows normally uses it for the Windows system volume.
- Important NTFS capabilities include:
  - Access-control lists and permissions
  - Journaling
  - Compression
  - Encrypting File System support
  - Disk quotas
  - Hard links and reparse points
  - Alternate data streams
  - Sparse files
  - Large files and volumes
- NTFS journaling helps preserve filesystem consistency by recording important metadata operations. It does **not** guarantee recovery of deleted, overwritten, or corrupted personal files and does not replace backups.
- NTFS is not literally Windows-only. Linux can read and write NTFS with suitable support; macOS generally reads NTFS but does not provide full native write support by default.
- **exFAT** is well suited to large removable drives and cross-platform exchange. It removes FAT32’s 4-GiB file-size limitation, but it lacks several NTFS features such as NTFS-style ACLs and metadata journaling.
- exFAT’s maximum supported file size is extremely large, but it is not literally limitless.
- Formatting creates a new filesystem structure and can make previous data inaccessible. A quick format and full format do different amounts of work, but neither should automatically be treated as secure erasure.
- A known or suspected malware USB device should not be connected to a primary computer merely to inspect it.

### Windows system-drive structure

- Windows is usually installed on `C:`, but `C:` is a convention rather than an absolute requirement.
- In a display such as `Windows (C:)`, **Windows** is the volume label and **C:** is the drive letter.
- Used space on `C:` is not necessarily all occupied by Windows. It can include applications, user profiles, personal data, temporary data, updates, restore points, paging data, and hibernation data.
- `C:\Users\<username>` normally contains a user’s profile. A profile includes personal folders, application settings, and a per-user registry hive.
- `C:\Users\Public` provides folders intended to be shared among users of the same computer. “Public” does not mean automatically accessible from the internet.
- `C:\Users\Default` is a hidden template used when Windows creates a new user profile.
- `C:\Users\<username>\AppData` stores per-user application information:
  - `Local` contains machine-specific settings, caches, and non-roaming data.
  - `LocalLow` is used by applications running in lower-integrity or restricted contexts.
  - `Roaming` contains settings intended to follow a domain user when roaming profiles are configured.
- `%APPDATA%` normally points to `AppData\Roaming`, while `%LOCALAPPDATA%` normally points to `AppData\Local`.
- Deleting an application’s AppData folder can remove local profiles, bookmarks, cookies, sessions, preferences, extension data, or unsynchronized information. A safer troubleshooting test is to close the application and **rename** the targeted folder so it can be restored.
- `C:\Program Files` normally contains 64-bit applications on 64-bit Windows.
- `C:\Program Files (x86)` normally contains 32-bit applications running through WOW64.
- Folder location is a convention, not absolute proof of an executable’s architecture.
- A 64-bit application is not automatically faster merely because it is 64-bit. Important differences include address space, memory availability, instruction-set capabilities, and binary compatibility.
- `C:\ProgramData` contains application information shared across users.
- `C:\PerfLogs` is available for performance logs and data-collector output.
- `C:\Windows` contains the operating system’s core files, shared components, logs, drivers, configuration data, and servicing infrastructure.
- On 64-bit Windows, `C:\Windows\System32` normally contains the primary **64-bit** Windows system executables and DLLs.
- `C:\Windows\SysWOW64` normally contains many **32-bit** system components used by the Windows 32-bit-on-Windows-64-bit compatibility layer.
- The names `System32` and `SysWOW64` appear backward because Microsoft preserved compatibility with older software.
- A `.dll` is a Dynamic-Link Library containing reusable code or resources that processes can load. A 32-bit process normally requires 32-bit DLLs, while a 64-bit process requires 64-bit DLLs.
- `C:\Windows\WinSxS` is the Windows component store. It supports Windows servicing, feature installation, updates, repair sources, component manifests, and multiple component versions.
- WinSxS can look larger than its true exclusive disk consumption because hard links may cause simplistic tools to count the same underlying file data multiple times.
- Windows component-store files should never be deleted manually. Supported tools such as DISM must be used when servicing is actually required.
- Hidden files and protected operating-system files are related but separate File Explorer settings. “Hidden” is a display attribute, not a security boundary; NTFS permissions control access.

### Windows Terminal and PowerShell navigation

- **Windows Terminal** is the host interface. PowerShell and Command Prompt are shells that can run inside it.
- A prompt such as `PS C:\Users\Brandon>` identifies PowerShell, the current drive, and the current working directory.
- In PowerShell, `dir` and `ls` are aliases for `Get-ChildItem`. They are not separate PowerShell implementations of the commands.
- `Get-Alias` and `Get-Command` can reveal what an alias or command name resolves to.
- `Get-ChildItem -Force` includes hidden items normally omitted from output, but it does not bypass NTFS permissions.
- `.` means the current directory; `..` means the parent directory.
- `cd ..` moves up one directory. `cd .` stays in the current directory.
- `cd \` moves to the root of the **current drive**, not a universal root for the entire computer.
- A **relative path** is interpreted from the current location, while an **absolute path** supplies the complete location beginning with a drive or provider.
- Paths containing spaces should be quoted, such as `Set-Location "C:\Program Files"`.
- In PowerShell, `$HOME` represents the current user’s home/profile location. `Set-Location $HOME` or `cd ~` is clearer than relying on shell-specific behavior of plain `cd`.
- `Clear-Host`, `clear`, `cls`, or commonly `Ctrl+L` clears the visible terminal screen but does not necessarily erase command history.
- `Ctrl+C` usually requests interruption of a running console command. It may not immediately terminate every process.
- `tree` displays directory structure recursively. `/F` includes filenames and `/A` uses simple text characters.

### NTFS permissions

- NTFS permissions are inspected through **Right-click → Properties → Security**.
- Basic permission groups include:
  - **Read:** view file data, attributes, and permissions.
  - **Read and execute:** read content and execute applicable files.
  - **List folder contents:** view item names within a folder.
  - **Write:** create or alter data depending on the object and advanced rights.
  - **Modify:** read, execute, write, change, and generally delete content.
  - **Full Control:** includes Modify plus powerful security actions such as changing permissions and taking ownership.
- The basic checkboxes are collections of more granular advanced permissions.
- **Modify** is usually preferable to Full Control when someone needs to work with data but should not administer its security.
- Windows permissions ultimately reference **security identifiers (SIDs)** rather than merely visible usernames.
- A **DACL** is the discretionary access-control list governing ordinary access.
- An **ACE** is an individual access-control entry within an ACL.
- Permissions can be **explicit**, meaning configured directly on an object, or **inherited** from a parent folder.
- Users commonly receive access through multiple security groups. Effective access results from their user SID, group SIDs, inherited entries, explicit entries, ownership, and the exact requested operation.
- Permissions should normally be assigned to security groups, with users added to the appropriate groups, instead of assigning every user directly.
- The statement “Deny always wins” is an oversimplification. Applicable deny entries are powerful, but effective access depends on the specific right, ACE ordering, inheritance, and group memberships.
- Canonical ACL order generally places explicit denies before explicit allows, followed by inherited denies and inherited allows.
- Avoid Deny entries unless a real requirement demands them; poorly planned denies make troubleshooting difficult.
- Ownership and Full Control are distinct. Owning an object does not simply mean every ordinary access right is automatically granted.
- Deleting an object can be authorized by Delete permission on the object or Delete Child permission on its parent, so deletion problems may require inspecting both locations.
- Network access to a shared folder evaluates both **share permissions** and **NTFS permissions**. The final network access is limited by the more restrictive combination.
- **Effective Access** in Advanced Security Settings is more reliable than inspecting only one visible permission entry.
- Recently changed group membership may require the user to sign out and back in so a new access token is created.

### Local Windows accounts and profiles

- A local account exists only in the security database of one Windows installation and is commonly represented as `COMPUTERNAME\username`.
- A domain account is commonly represented as `DOMAIN\username` and is centrally administered through Active Directory.
- A Microsoft account is a consumer cloud identity, while a Microsoft Entra account belongs to an organization’s cloud tenant.
- Local users can be managed through:
  - Settings → Accounts → Other users
  - Computer Management → Local Users and Groups
  - `lusrmgr.msc`
  - PowerShell LocalAccounts cmdlets
  - Traditional commands such as `net user`
- Local Users and Groups is not available on Windows Home editions.
- Creating an account creates its security identity, but Windows normally creates the complete `C:\Users\<username>` profile only when the user signs in for the first time.
- The account and profile are separate objects. Removing a user does not necessarily remove every profile artifact, and manually deleting a profile folder is not the correct general removal procedure.
- A newly created local user is normally a **standard user**, not an administrator.
- Administrative rights normally come from membership in the local Administrators group.
- Usernames, display/full names, descriptions, and SIDs serve different purposes. Renaming an account does not change its SID.
- Recreating a deleted username creates a new SID, so it does not automatically inherit permissions that referenced the old account.
- Groups provide scalable role-based authorization: **user → security group → resource permission**.
- Built-in accounts such as Administrator, Guest, DefaultAccount, and WDAGUtilityAccount may appear even when the user did not create them. They should not be casually deleted or enabled.
- Disabling an account is often safer than immediate deletion because it blocks use while preserving the identity for investigation or rollback.
- An administrator resetting another user’s password can affect EFS-encrypted files, stored credentials, private keys, and certain saved secrets. A password reset and a user changing a known password are not identical operations.

### PowerShell account creation and elevation

- PowerShell cmdlets normally use the `Verb-Noun` naming convention, such as `New-LocalUser`, `Get-LocalUser`, and `Remove-LocalUser`.
- `New-LocalUser -Password` expects a `System.Security.SecureString`, not an ordinary quoted `System.String`.
- `Read-Host -AsSecureString` masks interactive input and returns the expected type.
- A variable in PowerShell begins with `$`, such as `$password`.
- A variable is a named reference to a value or object held during the current PowerShell session or scope.
- Hardcoding passwords in commands, scripts, screenshots, notes, or Git repositories should be avoided.
- A `SecureString` is safer than visible plaintext input, but it should not be interpreted as perfect security under every platform and threat model.
- **Run as administrator** starts an elevated process after UAC authorization. An account belonging to Administrators and a currently elevated process are related but different states.
- Administrator elevation grants substantial power but does not automatically bypass every Windows protection or make the process equivalent to SYSTEM, TrustedInstaller, a domain administrator, or an Entra administrator.
- A standard user may receive a UAC credential prompt, while an administrator may receive a consent prompt, depending on policy.

### Windows troubleshooting mindset

- Administrative tools should be used as related views into one system:
  - Task Manager provides a quick live overview.
  - Resource Monitor provides deeper per-process resource details.
  - Reliability Monitor shows a timeline of failures, installations, and updates.
  - Event Viewer provides detailed event records.
  - Device Manager exposes hardware and driver state.
  - Services exposes background service state and configuration.
  - System Configuration isolates startup conflicts.
  - Disk Management exposes disks, partitions, and volumes.
- A disciplined workflow is: define the symptom, determine scope, reproduce it, record the exact time, collect evidence, form a hypothesis, make one reversible change, test, verify, and document.
- Observation should come before configuration changes. Making several changes simultaneously makes the actual cause difficult to determine.
- Event Viewer warnings and errors are not automatically evidence of a serious problem; relevance depends on timing, repetition, source, event ID, and the user’s symptom.
- Reversible actions—such as renaming configuration data or disabling an account—are preferable to immediate deletion when testing a theory.
