## 🧠 What I Learned / Key Takeaways

### Public vs. Private Subnets

- A subnet is not inherently "public" or "private."

- **Routing determines how the subnet behaves.**

A public subnet normally has:

    0.0.0.0/0 → Internet Gateway

A private subnet that requires outbound Internet connectivity commonly has:

    0.0.0.0/0 → NAT Gateway

- An EC2 instance in a public subnet still needs a **public IPv4 address or Elastic IP** to communicate directly with the IPv4 Internet through an Internet Gateway.

---

### Route Tables vs. Security Groups

Route tables answer:

> Where should this packet go?

Security groups answer:

> Is this traffic allowed?

These are two completely different responsibilities.

A network path can be perfectly valid while a security group still blocks the traffic.

---

### Security Groups Are Stateful

- Security groups are **stateful**.
- Return traffic for an allowed connection is automatically permitted.
- Removing an inbound rule prevents new connections that depend on that rule, although an already-established connection may remain alive.

A security-group reference such as:

    Private EC2 SG
    TCP 22 ← Bastion SG

means the private EC2 allows SSH connections from network interfaces associated with the referenced Bastion security group.

This is preferable to hard-coding the bastion's private IP when the architectural relationship is what matters.

---

### The VPC Local Route

Every VPC route table contains a local route for the VPC CIDR:

    10.69.0.0/16 → local

This does **not** mean "this subnet."

It represents the VPC CIDR and enables VPC routing between addresses contained within that VPC.

Example:

    Bastion
    10.69.0.21
         │
         │ 10.69.0.0/16 → local
         ▼
    Private EC2
    10.69.128.241

Even though these instances live in different subnets, their addresses are both inside:

    10.69.0.0/16

Therefore their traffic uses the VPC's local route.

---

### Longest-Prefix / Most-Specific Route Matching

AWS chooses the **most specific matching route**.

Given:

    10.69.0.0/16 → local
    0.0.0.0/0    → NAT Gateway

Traffic destined for:

    10.69.128.241

matches the `/16` route, so it stays local to the VPC.

Traffic destined for:

    8.8.8.8

does not match `10.69.0.0/16`.

It therefore uses:

    0.0.0.0/0 → NAT Gateway

Important:

`0.0.0.0/0` does not literally mean "the Internet."

It means **all IPv4 destinations**.

More-specific matching routes take precedence over it.

---

### NAT Gateway

The private EC2's normal Internet path is approximately:

    Private EC2
          ↓
    Private Route Table
          ↓
    0.0.0.0/0 → NAT Gateway
          ↓
    NAT Gateway
          ↓
    Internet Gateway
          ↓
    Internet

A **public NAT Gateway still depends on an Internet Gateway** for Internet connectivity.

This means removing the public subnet's:

    0.0.0.0/0 → IGW

also breaks Internet access for private instances relying on the NAT Gateway.

NAT Gateway and Internet Gateway are therefore not interchangeable.

The NAT Gateway allows private resources to **initiate outbound Internet connections** while using the NAT Gateway's public IP for that traffic.

It does not make the private EC2 directly reachable from unsolicited Internet connections.

## S3 Gateway VPC Endpoint

The biggest new concept today was understanding **VPC Endpoints**.

Before creating the endpoint, S3 traffic from the private instance could use the normal outbound path:

    Private EC2
          ↓
    0.0.0.0/0
          ↓
    NAT Gateway
          ↓
    Internet Gateway
          ↓
    Amazon S3

After creating the S3 Gateway VPC Endpoint, AWS added a route similar to:

    pl-63a5400a → vpce-...

The `pl-...` destination is an **AWS-managed prefix list** representing the S3 destination networks for the Region.

The private route table can therefore contain:

    10.69.0.0/16 → local
    pl-63a5400a   → S3 Gateway VPC Endpoint
    0.0.0.0/0    → NAT Gateway

AWS can now make different routing decisions depending on the destination:

    Destination inside VPC
            ↓
          local

    Destination = S3
            ↓
      S3 Gateway Endpoint

    Other external destination
            ↓
        NAT Gateway

S3 traffic using the Gateway VPC Endpoint does **not** need to traverse the NAT Gateway or Internet Gateway/public Internet path.

Instead:

    Private EC2
          ↓
      VPC routing
          ↓
    S3 Gateway VPC Endpoint
          ↓
      AWS network
          ↓
       Amazon S3

The S3 Gateway Endpoint does **not** make S3 part of:

    10.69.0.0/16 → local

Instead, AWS provides a completely separate route into the S3 service.

---

### Gateway Endpoint Route-Table Associations

Gateway endpoints are associated with **route tables**.

The relationship is:

    Subnet
       ↓ uses
    Route Table
       ↓ associated with
    S3 Gateway Endpoint

Therefore, if a subnet uses a route table associated with the S3 Gateway Endpoint, resources in that subnet can use the S3 endpoint route.

A single S3 Gateway Endpoint can service multiple route tables and therefore multiple subnets.

I do **not** need:
- One endpoint per EC2 instance.
- One endpoint per subnet.

I can associate multiple route tables with the same Gateway Endpoint.

---

### Gateway vs. Interface VPC Endpoints

I initially selected an S3 service that showed:

    Type: Interface

That was not the endpoint type needed for this particular exercise.

An **Interface Endpoint** works by creating endpoint network interfaces (ENIs) in selected subnets.

A **Gateway Endpoint** for supported services such as S3 and DynamoDB integrates with the VPC's **route tables**.

This is why selecting the S3 Gateway Endpoint caused AWS to ask which route tables should be associated with it.
