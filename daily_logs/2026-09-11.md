## 🧠 What I Learned / Key Takeaways
- Subnet math end to end: picking a non-default `/16` VPC CIDR, carving `/24` subnets, and why AWS reserves 5 addresses per subnet instead of 2
- Why a NAT Gateway must live in the public subnet (it needs its own route to the IGW to translate and forward traffic) — corrected an initial instinct that it belonged in the private subnet
- NAT Gateways have no security group of their own — access is controlled by route tables (who can reach it) and the instances' own security groups (what they're allowed to send), not a firewall on the gateway
- Nothing from the internet can ever reach a private subnet directly, regardless of security group rules — there's no route in, full stop
- SG-to-SG chaining: referencing another security group as a source instead of an IP, so access follows group membership dynamically rather than a static address
- SSH key pairs are authentication only, not authorization; the private key never leaves the local machine, it signs a challenge, and the public key (in the instance's authorized_keys) verifies it
- SSH agent forwarding (`-A` flag) lets a two-hop bastion connection work without ever placing a private key file on the bastion — proved this live with a successful private-instance login using zero key material on the bastion itself
- Regional NAT Gateway (new AWS feature, Nov 2025) exists as a VPC-level alternative to per-AZ Zonal NAT Gateways — noted as worth knowing for interviews, deliberately not used today to keep the lesson focused
- Elastic IPs are free only while attached to a running resource; an orphaned EIP after deleting a NAT Gateway keeps billing until manually released — VPC deletion does not clean this up automatically
- Found a dormant, `AdministratorAccess`-scoped, 112-day-old static IAM access key sitting locally — flagged as a real least-privilege risk, deferred rotation until confirmed safe to do so

- `ssh-add` to load multiple private keys into the local SSH agent
- `ssh -A ec2-user@<public-ip>` for the bastion connection with agent forwarding enabled

- `ip addr` and `whoami` on EC2 instances to confirm network identity and session context
- `ping -c 4 8.8.8.8` to verify NAT Gateway outbound connectivity from a private instance
